第1章：アーキテクチャの鳥瞰図（Next.js × Supabase）

▼

1-1 Webの3層構造とSupabaseの役割

💡平易な解説：レストランに例えるWebシステム

Webアプリの構成はレストランによく似ています。

  • ブラウザ（顧客のテーブル）： 画面を見たり注文ボタンを押したりする場所。利用者のスマホやPC。
  • Next.jsサーバー（厨房・ホールスタッフ）： レシピに従って料理（HTML/データ）を組み立て、配膳する。
  • Supabase（巨大な食材倉庫・金庫）： 大切なデータ（ユーザー情報、畑の畝データ）が厳重に保管されているデータベース。

昔のWebは「注文ごとに厨房（サーバー）へ行って料理を全部作り直す」方式でしたが、現在のNext.jsとReactは「テーブル（ブラウザ）側で賢く一部の具材だけを交換する」ことができるハイブリッドな構成になっています。

1-2 実コード解剖：Supabaseクライアントの初期化

このプロジェクトでは、ブラウザ用とサーバー用でSupabaseの初期化コードを明確に分けています。まずはブラウザ用クライアントを見てみましょう。

📁 utils/supabase/client.ts
import { createBrowserClient } from '@supabase/ssr';
import type { Database } from '@/types/supabase';

export function createClient() {
  const isPreviewOrCI =
    process.env.CI === 'true' ||
    process.env.VERCEL_ENV === 'preview' ||
    (process.env.VERCEL === '1' && !process.env.NEXT_PUBLIC_SUPABASE_URL);

  const url =
    process.env.NEXT_PUBLIC_SUPABASE_URL ||
    (isPreviewOrCI ? 'https://placeholder.supabase.co' : '');
  const anonKey =
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY ||
    (isPreviewOrCI ? 'mock-anon-key-for-preview-and-ci' : '');

  if (!url || !anonKey) {
    throw new Error(
      'Missing Supabase environment variables: NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY must be configured.'
    );
  }

  return createBrowserClient<Database>(url, anonKey);
}
🔍コードの解剖ポイント
  • createBrowserClient<Database>: ブラウザの Cookie を自動的に使って認証セッションを維持する特別なクライアントです。<Database> という型（ジェネリクス）を渡すことで、「テーブル名やカラム名」をタイポした瞬間にTypeScriptが赤線で警告してくれるようになります。
  • NEXT_PUBLIC_...: Next.jsでは、接頭辞 NEXT_PUBLIC_ がついた環境変数だけが「ブラウザ（JavaScript）」にバンドルされて公開されます。それ以外の変数はサーバー上でしか参照できません。

1-3 AIに頼る時の落とし穴（AIあるある）

⚠️危険：service_role キーをクライアントコードで使ってしまう

AIがやりがちなミス：「Supabaseの権限エラー（RLSエラー）が出ました」とAIに相談すると、AIが手っ取り早く解決するために SUPABASE_SERVICE_ROLE_KEY（すべてのセキュリティを無視できるマスターキー）をクライアント側のコードに記述してしまうことがあります。

// ❌ 絶対にやってはいけない例 (ブラウザで秘密キーが見えてしまう)
const supabase = createClient(process.env.NEXT_PUBLIC_SUPABASE_URL, process.env.SUPABASE_SERVICE_ROLE_KEY);

初心者の着眼点： ブラウザから呼ぶSupabaseクライアントには、必ず NEXT_PUBLIC_SUPABASE_ANON_KEY（一般公開キー）のみを渡し、アクセス権限はSupabaseの「Row Level Security (RLS)」ポリシーで守るのが鉄則です。

第2章：Next.js App Routerの境界線（Server vs Client）

▼

2-1 Server Component と Client Component の物理的な違い

💡平易な解説：印刷された雑誌 vs タッチパネル画面

Next.js App Router では、すべてのコンポーネントがデフォルトで「Server Component」です。

  • Server Component（印刷された雑誌）： サーバー上で完成したHTMLを生成してブラウザに送ります。ブラウザにJavaScriptコードが送られないため、読み込みが超高速でセキュアですが、クリックしてもページ遷移以外のアニメーションや状態変化はできません。
  • Client Component（タッチパネル画面）： 先頭に 'use client' を書くことで、ブラウザにJavaScriptコードを送り、ボタンクリックや文字入力（State）に応答できるようにします。

2-2 実コード解剖：遅延読み込み (dynamic) と SSR 制御

講師用ダッシュボードのページを見てみましょう。ここでは巨大なコンポーネントを next/dynamic で遅延ロードしています。

📁 app/teacher/dashboard/page.tsx
'use client';

import { useEffect, useState } from 'react';
import dynamic from 'next/dynamic';
import { SproutLoader } from '@/components/SproutLoader';

// 🌟 重量級コンポーネントをクライアント専用遅延読み込み (ssr: false) に分割 🌟
const TeacherTaskBoardView = dynamic(() => import('@/components/teacher/TeacherTaskBoardView'), {
  ssr: false,
  loading: () => <SproutLoader />,
});
const TeacherFarmCanvasView = dynamic(() => import('@/components/teacher/TeacherFarmCanvasView'), {
  ssr: false,
  loading: () => <SproutLoader />,
});

export default function TeacherDashboardPage() {
  const [activeTab, setActiveTab] = useState('tasks');

  return (
    <div>
      {activeTab === 'tasks' && <TeacherTaskBoardView />}
      {activeTab === 'farm' && <TeacherFarmCanvasView />}
    </div>
  );
}
🔍コードの解剖ポイント
  • ssr: false: 「このコンポーネントはサーバー側でHTMLを組み立てず、ブラウザに届いてから初めて実行してください」という指示です。Canvas描画やドラッグ＆ドロップ（dnd-kit）のように、ブラウザ固有の window や document に依存するライブラリを使う場合、サーバー側で動かすとエラー（Hydration Mismatch）になるため、これを防いでいます。
  • loading: () => <SproutLoader />: ブラウザがJavaScriptファイルをダウンロードしている間、真っ白な画面ではなくスプラウト（芽）のアニメーションを表示してユーザーを待たせない工夫です。

2-3 AIに頼る時の落とし穴（AIあるある）

⚠️危険：エラーが出たら思考停止で全ファイルに 'use client' を貼る

AIがやりがちなミス： Next.jsで開発中、Error: Event handlers cannot be passed to Client Component props... といったエラーが出た際、AIに「直して」と頼むと、ルートの layout.tsx や page.tsx の先頭すべてに 'use client' を付与してしまうことがあります。

初心者の着眼点： 画面全体を 'use client' にしてしまうと、せっかくのNext.jsの高速性（Server Componentの利点）が失われ、アプリ全体のJavaScriptファイルサイズが肥大化します。 「フォーム入力やボタンなど、インタラクションが必要な最小の末端部品だけを 'use client' に切り出し、親はServer Componentのまま保つ」のが正しい設計です。

第3章：TypeScriptの型安全性（any を滅ぼす理由）

▼

3-1 なぜ any を使ってはいけないのか？

💡平易な解説：危険物検査を通さない「何でもOKのフリーパス」

TypeScriptの最大のメリットは、「画面を動かす前に、コードの書き間違いやデータ不整合をコンパイラが見つけて教えてくれること」です。

しかし、型に any を指定すると、コンパイラは「中身が何であれ検査をスキップする」状態になります。これは空港の手荷物検査で「何が入っていても無検査で通す」ようなものです。 その結果、本番環境でユーザーが使っている最中に TypeError: Cannot read properties of undefined となって画面がクラッシュします。

3-2 実コード解剖：RFC 7807 準拠のレスポンスとジェネリクス

プロジェクト内でAPIレスポンスの型を統一している lib/apiResponse.ts を見てみましょう。

📁 lib/apiResponse.ts
import { NextResponse } from 'next/server';

export interface ProblemDetails {
  type: string;
  title: string;
  status: number;
  detail?: string;
  invalidParams?: Array<{ name: string; reason: string }>;
  [key: string]: unknown;
}

export class ApiResponse {
  /**
   * 成功レスポンス（ジェネリクス <T> で返却データの型を保証）
   */
  static success<T>(data: T, status = 200, init?: ResponseInit): NextResponse<T> {
    return NextResponse.json(data, { status, ...init });
  }

  /**
   * RFC 7807 に準拠した統一エラーレスポンス
   */
  static badRequest(detail: string, invalidParams?: Array<{ name: string; reason: string }>) {
    return this.problem(400, 'Bad Request', detail, { invalidParams });
  }
}
🔍コードの解剖ポイント
  • success<T>(data: T): <T> は「ジェネリクス（型の変数）」です。ユーザー情報を返すときは User 型、タスクを返すときは Task[] 型など、渡されたデータの型がそのまま NextResponse<T> に引き継がれます。呼び出し側は「このAPIは何を返すのか」を厳密に把握できます。
  • [key: string]: unknown: any ではなく unknown を使っています。unknown は「何が入っているか分からないが、使う前に typeof などで型チェックを強制する」型です。安全性を一切損ないません。

3-3 AIに頼る時の落とし穴（AIあるある）

⚠️危険：(data as any) で型エラーを「黙らせる」

AIがやりがちなミス： SupabaseのJOINクエリなどで型定義が一致しないとき、AIはよく const user = (data as any).user; や as unknown as MyType というキャストを行います。

初心者の着眼点： as any はTypeScriptの型チェッカーを「強制的に沈黙」させる行為です。DBのカラム名がリネームされたりNULLが混入した際、ビルドは通るのに画面が真っ白になります。 Supabase CLIの supabase gen types typescript を使ってDBと同期した自動生成型（Database）を適用するか、後述する Zod によるバリデーションを挟むのが正攻法です。

第4章：React Hooksと状態管理（再レンダリングの仕組み）

▼

4-1 State と再レンダリングの本質

💡平易な解説：スコアボードが書き換わると全員が顔を上げる

Reactのコンポーネントは、ただの「関数」です。 useState で管理されている「状態（State）」が更新されると、Reactはそのコンポーネント関数をもう一度最初から最後まで実行（再レンダリング）し、画面のDOMを書き換えます。

スコアボード（State）の点数が変わると、観客や審判（子コンポーネントたち）が一斉に顔を上げて反応するイメージです。このとき、適切に関数をメモ化（useCallback）しておかないと、関係ない子コンポーネントまで無駄に再実行されて画面がカクつきます。

4-2 実コード解剖：カンバン操作をカプセル化したカスタムフック

タスク管理画面のロジックを抽出した hooks/useKanbanBoard.ts の一部を抜粋します。

📁 hooks/useKanbanBoard.ts
'use client';

import { useState, useCallback } from 'react';
import { supabase } from '../lib/supabase';
import { Task, ColumnType } from '../types/task';

export function useKanbanBoard(columns: ColumnType[]) {
  const [tasks, setTasks] = useState<Task[]>([]);
  const [isLoading, setIsLoading] = useState<boolean>(true);

  // タスク取得関数を useCallback で包んで無駄な再生成を防ぐ
  const fetchTasks = useCallback(async () => {
    try {
      const { data: { user } } = await supabase.auth.getUser();
      if (!user) return;

      const { data } = await supabase
        .from('tasks')
        .select('*')
        .is('deleted_at', null)
        .order('created_at', { ascending: false });

      if (data) setTasks(data as unknown as Task[]);
    } finally {
      setIsLoading(false);
    }
  }, []); // 依存配列が空: この関数インスタンスは初回生成から変化しない

  return { tasks, isLoading, fetchTasks };
}
🔍コードの解剖ポイント
  • カスタムフック（useKanbanBoard）: UI（JSXの見た目）と「データ取得・更新のロジック」を分離しています。これにより、コンポーネント側は const { tasks } = useKanbanBoard(...) と呼ぶだけで済み、コードの見通しが劇的に良くなります。
  • useCallback(fn, []): 通常、コンポーネントが再レンダリングされると関数も新しく作り直されます。useCallback を使うことで、中身が変わらない限り「同じ関数の参照」を維持し、子コンポーネントへの余計な再レンダリング伝播を阻止します。

4-3 AIに頼る時の落とし穴（AIあるある）

⚠️危険：useEffectの依存配列にオブジェクトやStateを入れて無限ループ

AIがやりがちなミス： useEffect 内でStateを更新しているのに、そのStateや新しいオブジェクト（例: [tasks] や { id }）を依存配列に含めてしまい、「State更新 → 再レンダリング → useEffect発火 → State更新...」 の無限ループでブラウザがフリーズします。

初心者の着眼点： 「データフェッチはマウント時の1回だけでいいのか？」「どの値が変わった時だけ再取得すべきか？」を意識し、関数を useCallback でメモ化するか、不要な useEffect 自体を減らす設計を心がけましょう。

第5章：バリデーションと多層防御（Zodによる境界防壁）

▼

5-1 多層防御：UI検証 vs サーバーAPI検証 vs DB制約

💡平易な解説：テーマパークのチケット改札

セキュリティとデータ品質を守るには、3つの防壁が必要です。

  • 第1の壁（UI / フォーム）： 入力漏れをその場で赤文字表示して親切に教える（UX向上目的。悪意があれば簡単にバイパス可能）。
  • 第2の壁（APIルート / Zod）： サーバーの入口で不正なデータ形式や権限不足を完全にブロック（セキュリティ防壁）。
  • 第3の壁（DB / RLS・制約）： 万が一APIのバグがあっても、DBレベルで他人のデータを書き換えさせない最後の砦。

5-2 実コード解剖：Zod による厳格なリクエストパース

チケット付与APIの app/api/tickets/grant/route.ts では、スキーマ検証ライブラリ Zod を使って堅牢に検証しています。

📁 app/api/tickets/grant/route.ts
import { z } from 'zod';
import { ApiResponse } from '@/lib/apiResponse';

// 1. Zod スキーマで許容するデータの形を宣言
const grantTicketRequestBodySchema = z.object({
  studentId: z
    .string()
    .min(1, '受講生IDは必須です')
    .regex(/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i, {
      message: '有効なUUID形式を指定してください',
    }),
  amount: z
    .number()
    .int('整数を指定してください')
    .positive('1以上を指定してください')
    .max(10, '一度に付与できるチケットは10枚までです')
    .default(1),
});

export async function POST(request: Request) {
  const rawBody = await request.json().catch(() => null);

  // 2. safeParse で安全に検証（例外を投げずに success: false を返す）
  const parseResult = grantTicketRequestBodySchema.safeParse(rawBody);

  if (!parseResult.success) {
    const issue = parseResult.error.issues[0];
    return ApiResponse.badRequest(issue?.message || '不正なリクエストです');
  }

  // 3. ここを通れば studentId は確実に UUID 文字列、amount は 1〜10 の整数が保証される
  const { studentId, amount } = parseResult.data;
  ...
}
🔍コードの解剖ポイント
  • z.object({...}): 「どんな型か」だけでなく「UUID形式か」「1以上10以下の正の整数か」といった業務ルール（ドメイン制約）まで実行時に検証します。
  • .safeParse(): .parse() を呼ぶとエラー時にアプリが例外をスロー（クラッシュ）してしまいますが、.safeParse() なら安全に結果オブジェクトを受け取って上品な400エラーJSONを返せます。

5-3 AIに頼る時の落とし穴（AIあるある）

⚠️危険：フロントのバリデーションだけで安心してサーバー側を素通しする

AIがやりがちなミス： フォーム側で required や disabled をつけたから大丈夫だと判断し、APIルート側では const { studentId, amount } = await req.json(); とダイレクトにDBへ渡すコードを生成することが多々あります。

初心者の着眼点： ブラウザの開発者ツールや curl コマンドを使えば、フロントエンドのバリデーションは誰でも1秒で突破できます。「フロントエンドのチェックは親切心（UX）、サーバーサイドのチェック（Zod）は命綱（セキュリティ）」と心に刻みましょう。
